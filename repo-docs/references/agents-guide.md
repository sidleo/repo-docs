# AGENTS.md：协作规则写作规范

## 目标与篇幅

让贡献者和 Agent 知道“在这个项目中应怎样做修改、怎样验证、怎样交付”。默认标题用 `# 项目协作规范`；用户要求 `Repository Guidelines` 或其他标题时沿用指定标题。

中文正文通常控制在 **600–1200 字**，小项目更短；已有必要规则较多时可以超出，不能为了字数删掉约束。长规则可引用仓库内已有专题文档，链接旁写明何时读取。不要把英文的 200–400 words 直接换算为中文词数。

只保留对当前项目有效且能改变行动的规则。项目背景、功能清单、安装教程、架构介绍和路线图放 README.md；此处用简短链接指向它们。

## 按实际项目选用的章节

| 章节 | 应写什么 |
| --- | --- |
| 适用范围 | 指令覆盖的目录；相关子目录规则与模块差异。只陈述宿主/项目已明确的作用机制。 |
| 修改边界 | 哪些模块承接哪些改动，生成文件如何再生成，公开接口/数据契约有哪些约束。目录只写与改动有关的部分。 |
| 开发与验证 | 贡献者最常用的检查/测试/构建入口及工作目录；完整环境搭建链接至 README.md。 |
| 风格与命名 | 真实缩进、命名、格式化/lint 工具及关键例外；优先引用配置，避免重复整份工具规则。 |
| 测试要求 | 已有框架、测试位置、命名和改动验证方式；覆盖率门槛仅在项目明确配置或要求时出现。 |
| 提交与 PR | 明确的提交约定、PR 模板、验证结果及按改动需要的截图/关联问题。只观察到的习惯标为建议。 |
| 特殊工作流 | 数据口径、SQL 预览、模板发布、生成代码等项目已有约束，以及触发时应读的规范。 |
| 配置与操作边界 | 密钥、外部写入、依赖升级或数据变更的项目规则，基于已有约定写，不发明审批流程。 |

根据项目裁剪章节。没有独立资产目录、测试或构建系统就省略对应结构，不预设 `src/`、`tests/`、`npm test` 或 Docker。

## 写法

- 用行动句写规则：有配置证据时写“修改 Python 代码后执行 `ruff check .`”；不要只写“注意代码质量”。
- 把事实转成行为：已确认的生成文件应写“修改源模板后重新生成产物”，而不只是“这里存放生成文件”。
- 默认不把个人偏好变成项目强制要求。新建议显式写“建议”；现有强制规则保留原力度。
- 没有足够提交历史时，说明尚无可归纳的约定；可建议清楚描述改动目的，但不能声称现行规则要求 `feat:` / `fix:`。
- 缺少自动测试时，说明可用的手工验证或现有校验入口；若两者都没有，直说未发现验证入口。
- 一个规则保留一个权威位置；需补充上下文时链接至 README.md 或已有专题规范。关键验证入口可就地保留。

## 空项目或非代码项目

空项目写已确认的工作约定、现有文件的维护方法以及当前验证入口状况。项目用途待确认时把问题留在交付说明。非代码项目围绕实际交付物写命名、源数据/模板、输出位置及核验方式。

生成后检查：每条规则是否有依据、是否能执行、是否只适用于它声称的范围；删除“通用最佳实践”堆砌与不适用章节。
