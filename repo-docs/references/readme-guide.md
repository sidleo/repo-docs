# README.md：项目说明写作规范

## 目标与篇幅

让第一次接触项目的人知道：**这是什么、能解决什么问题、怎么开始用、下一步去哪里看**。用实际项目名称作一级标题，正文用中文；保留已有品牌名、徽章和需要保留的原文。

篇幅以完整覆盖一条最短使用路径为准，通常 **800–2000 字**；简单脚本或文档项目可以更短。避免为了填满结构重复规则，协作要求链接至 AGENTS.md。

## 按实际项目选用的章节

| 章节 | 应写什么 |
| --- | --- |
| 项目简介 | 一至三句话说明用途、使用者、核心输入与输出。不要仅罗列技术栈。 |
| 主要能力与边界 | 已实现的关键能力、适用场景及影响使用选择的限制。计划功能单独标明或省略。 |
| 快速开始 | 环境前提 → 安装/准备 → 必需配置 → 最小运行 → 如何判断成功。只写存在的入口。 |
| 使用示例 | 一条可复用的典型操作；参数、输入输出与产物位置有项目依据。长示例链接到现有示例文件。 |
| 项目结构 | 只列关键实际路径，通常两至三层，解释模块职责、资源、测试及输出位置。 |
| 配置说明 | 公开变量名、用途、是否必需、非敏感默认值；敏感值用占位符，说明从哪里安全配置。 |
| 开发与测试 | 已有开发、构建、格式化和测试命令；注明工作目录及前提，协作规则链接至 AGENTS.md。 |
| 架构或数据流程 | 仅在帮助理解或使用时添加，说明真实模块/系统之间的输入输出关系。 |
| 常见问题与限制 | 有证据的现象、适用条件、检查和解决方法；不把本轮临时机器故障写成长期项目限制。 |
| 贡献与许可证 | 指向已有规范及 LICENSE；不存在许可证时不声明 MIT、Apache 或其他授权。 |

文档/数据项目可以用“准备材料、执行步骤、交付物、核验方式”替代软件安装与服务启动。多模块仓库给出模块选择和各自入口，避免混用工作目录与依赖管理器。

## 命令与示例的可信度

- 先确认命令的定义，再选最短可用流程。包管理器以锁文件、项目约定及 CI 为依据，版本要求来自项目声明，不能凭记忆补“最新版”。
- 代码块写明语言，保持命令可复制；切换目录必须明确。以变量名或明显占位值演示配置，不放真实凭据。
- 确认输入/输出名称、默认端口和产物目录；未执行的示例不能编造成功日志。示意数据标明“示意”，不宣称实测结果。
- 命令从配置确认但因环境未执行时，在交付说明中交代；若限制本身是项目的持久前提，则在快速开始写清。
- 没有可运行代码时，直说当前为文档/规划阶段，解释如何阅读和使用已有材料；不能造出安装命令、服务地址或功能截图。

## 更新既有说明

保留仍有效的上手流程、人工章节、许可证说明和公开链接。只在有项目依据时纠正现状。AGENTS.md 若缺失且本次只要求 README.md，不添加指向不存在文件的链接；可以在交付说明建议补充。

完成后沿“新读者第一次使用”的路径逐步核对：前提能找到、入口真实、参数齐全、成功判断可解释、相关链接可到达。无法确认的关键信息简短列入交付说明，不用模板占位词填进正文。
